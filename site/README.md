# Штаб CS2 «Ушибу ногами»

Закрытый маршрутный штаб команды: ближайший матч, подтверждённые факты, блокеры, действия,
тренировки, карты и соперники. Исследовательский раздел «Данные» открывается отдельно и не
формирует оперативные советы автоматически.

## Локальный запуск и проверки

Нужен Node.js 20 или 22.

```bash
npm ci
npm test
```

`npm test` последовательно проверяет JSON-контракт, unit-тесты и браузерные сценарии. Команды
можно запускать раздельно:

```bash
npm run validate:content
npm run test:unit
npm run test:e2e
```

Playwright сам поднимает тестовый сервер. Порт можно переопределить, если стандартный занят:

```bash
PLAYWRIGHT_PORT=4174 npm test
PLAYWRIGHT_PORT=4174 node test/server.mjs
# → http://127.0.0.1:4174/#/seichas
```

`test/server.mjs` — безавторизационная UI-фикстура, а не копия production auth. Реальный вход с
`Secure` cookie проверяется в HTTPS- или Vercel-совместимой локальной среде; ослаблять cookie ради
локального HTTP нельзя.

## Маршруты

Основные разделы:

- `#/seichas` — ближайший предстоящий матч относительно текущей даты;
- `#/matchi` — четыре наших матча;
- `#/trenirovki` — подтверждённые сессии и фактический отчёт;
- `#/karty` — семь карт и состояние опубликованных протоколов;
- `#/soperniki` — четыре соперника с методологической оговоркой;
- `#/statistika` — нейтральный исследовательский раздел «Данные».

Детали доступны по `#/match/:id`, `#/karty/:map` и `#/soperniki/:team`. Старые адреса
канонизируются автоматически. `pravila.html` перенаправляет на `index.html#/seichas`.

## Оперативный контент

Единственный репозиторный источник оперативных утверждений —
`assets/data/operations.json`. Его схема — `assets/data/operations.schema.json`; проверка —
`scripts/validate-content.mjs`.

Карточки имеют только пять типов:

- `fact` — подтверждённый факт с источником, датой и уверенностью;
- `projection` — проекция с выборкой и обязательной оговоркой;
- `decision` — принятое человеком решение с владельцем и evidence IDs;
- `unknown` — честный пробел, владелец и способ закрытия;
- `action` — проверяемое действие с владельцем, сроком и зависимостями.

Любая правка данных должна проходить `npm run validate:content`. Валидатор отклоняет лишние поля,
неверные даты, пустых ответственных, дубликаты и неизвестные ссылки ID. ID нельзя менять без плана
миграции: они используются в маршрутах и ключах общего состояния.

Каждый матч явно связывает статус вето через `vetoCardId` с карточкой `unknown` или `decision`.
`decision.evidenceIds` могут ссылаться только на `fact`/`projection`, а `action.dependsOn` — только
на `unknown`/`action`; валидатор проверяет не только наличие ID, но и тип связи.

Whoajor лежит в `assets/data/whoajor/` и загружается лениво только для маршрутов `#/statistika…`.
`current.json` — некешируемый указатель, versioned assets — immutable. Не редактируйте versioned
снимок вручную. Основные таблицы карт получают текущий пул из `operations.maps`; workshop/hostage
карты и сырые corpus counts остаются только в качестве данных/диагностики, а не оперативным пулом.

## Состояние

Чеклисты, фактические заметки и структурированный счёт используют общий v4 API `api/state` через
`assets/js/store.js`. Единственный production-объект состояния — приватный Blob `state/team.json`.
Старые персональные Blob-объекты API не читает и не изменяет.

`GET /api/state` возвращает только:

```json
{
  "me": { "id": "player-id", "nick": "Ник" },
  "state": { "checks": {}, "notes": {}, "scores": {} },
  "revision": 0
}
```

`POST /api/state` принимает тело не больше 32 KiB с `mutationId` и непустым массивом `operations`.
Допустимы только известные из `operations.json` ключи и операции `check.set`, `note.set`, `score.set`.
Счёт хранится как `{ "ours": 13, "theirs": 8, "played": true }`, а не строкой. Успех возвращает
`{ "ok": true, "revision": 1 }`; известный повтор `mutationId` возвращает его исходную ревизию.
История содержит точный непрерывный горизонт последних 256 мутаций, поэтому дедупликация с
исходной ревизией гарантирована только внутри этого окна.

Клиент сначала сохраняет неизменяемую FIFO-очередь локально, применяет её поверх подтверждённого
снимка и удаляет только после валидного ответа сервера. Сетевые ошибки, `409` и `5xx` повторяются
автоматически; общая кнопка «Повторить синхронизацию» запускает попытку вручную. На закрытии вкладки
отправляется копия через beacon — исходная запись остаётся до обычного подтверждения. Очередь
привязана к подтверждённому `me.id`: запись одного пользователя не отправляется от имени другого,
а после повторного входа того же пользователя восстанавливается.

Ключи формируются стабильно:

- действия матча — ID карточки, например `action-m01-confirm-time`;
- заметка матча — `match-<id>-note`;
- счёт матча — `match-<id>-score`;
- отчёт тренировки — `training-<map>-report` и `training-<map>-report-complete`.

## Дизайн и доступность

Тёмная industrial/editorial тема живёт в `assets/css/theme.css`; шрифты локальные. Основная
навигация — обычные ссылки, интерактивы имеют доступные подписи и touch-target не меньше 44×44 px.
Рендер строит DOM через `createElement`/`textContent`; inline styles не используются. Ошибки
оперативного контента и данных объявляются через live status и предлагают повторную загрузку.

## Доступ и деплой

Production: <https://ushibu-nogami-hq.vercel.app>. Middleware закрывает весь штаб сессией;
`api/*` дополнительно проверяют её сами. Обязательные переменные Vercel:

| Переменная | Назначение |
|---|---|
| `TEAM_USERS` | JSON-массив пользователей с хешами паролей и версиями сессий |
| `AUTH_SECRET` | секрет подписи сессий |
| `BLOB_READ_WRITE_TOKEN` | доступ к приватному Blob-стору |

Если `TEAM_USERS` или `AUTH_SECRET` отсутствуют, сайт отвечает 503. Пароль хешируется существующей
`hashPassword()` из `lib/auth.js`. Формат пользователя:

```json
{
  "id": "player-id",
  "nick": "Ник",
  "hash": "pbkdf2$210000$<salt>$<hash>",
  "sessionVersion": 1
}
```

Для старой конфигурации отсутствие `sessionVersion` нормализуется в `1`. При смене пароля нужно
одновременно заменить `hash` и увеличить `sessionVersion`: только так все ранее выданные cookie
этого пользователя немедленно перестанут проходить проверку. Удаление пользователя также отзывает
его сессию. Login допускает не более 10 зарезервированных попыток за скользящие 5 минут на
HMAC-псевдоним IP; хранилище или его CAS недоступны — вход закрывается без проверки пароля.

## Локальная миграция v3 → v4

Скрипт работает только с явно заданным локальным JSON, ничего не загружает из Blob и по умолчанию
ничего не записывает. Сначала выполните dry-run:

```bash
node scripts/migrate-state-v3.mjs --input /absolute/path/team-v3.json
```

В stdout будут `preview` и отчёт о сохранённых/отброшенных ключах. Для отдельного результата:

```bash
node scripts/migrate-state-v3.mjs \
  --input /absolute/path/team-v3.json \
  --output /absolute/path/team-v4.json
```

Output создаётся с правами `0600` и exclusive-create: существующий файл и input никогда не
перезаписываются. Legacy score переносится только из строгой строки `0..99:0..99`; остальные
значения счёта отражаются в отчёте как отброшенные. Corrupt v4 не очищается автоматически — API
закрывается с общей ошибкой до ручного восстановления.

### Backup, rollout и rollback

Task 3 не выполняет production backup, migration или deploy. Для будущего rollout:

1. Назначить короткое наблюдаемое окно и не допускать одновременно работающих v3 writers.
2. Скачать приватный `state/team.json` в защищённый локальный файл, сохранить его ETag и проверить,
   что backup читается как JSON; Blob нельзя временно делать публичным.
3. Выполнить dry-run над backup, изучить отчёт и отдельно создать v4-файл. До deploy не заменять
   production-объект.
4. Развернуть v4-код и v4-состояние согласованно, проверить вход, `GET /api/state`, одну тестовую
   мутацию, рост `revision` и отсутствие внутренних деталей в ошибках.
5. На время наблюдения сохранить исходный backup неизменным. Если после rollout уже появились v4
   записи, не восстанавливать старый v3 вслепую: оставить v4-совместимый код, экспортировать
   актуальное состояние и согласовать forward-fix. Откат на v3 допустим только при остановленных
   writers и когда подтверждено, что новых v4 изменений нет.

Остаточный клиентский риск: `localStorage` общий для вкладок, а межвкладочной блокировки в этой
версии нет. Две вкладки одного пользователя могут одновременно перезаписать локальную offline-
очередь; серверный CAS защищает Blob, но не исправляет такую локальную гонку.

```text
index.html                       оболочка и семантическое меню

assets/js/stats-core.js          маршруты и загрузка Data
assets/js/stats.js               нейтральный Data renderer

lib/state-core.js                строгая схема, миграция и применение mutation

scripts/validate-content.mjs     Ajv + семантические проверки
test/                            unit и Playwright acceptance tests
```
