# Полный импорт stats.whoajor.com

## Цель

Однократно перенести в репозиторий все исходные данные, доступные через публичные GET-endpoint'ы
`https://stats.whoajor.com/api/`, построить из них проверяемую SQLite-базу и добавить источник в
существующую KB. Владелец задачи подтвердил разрешение сообщества на полный импорт.

Результат считается готовым только тогда, когда можно доказать полноту обхода, повторно построить
SQLite из сохранённых HTTP-ответов и проследить любое число в KB до конкретного ответа API.

## Что означает «все данные»

Импортируем все первичные сущности и все конечные публичные GET-представления без перебора
комбинаторного множества фильтров `tag × map × side × from × to`.

В снимок входят:

1. `/api/meta`, `/api/tags`, `/api/draft-config`;
2. полный `/api/matches` с пагинацией и `/api/matches/{match_id}` для каждого матча;
3. полный `/api/leaderboard`;
4. для каждого SteamID из объединения leaderboard, матчей и draft:
   `/summary`, `/maps`, `/weapons`, `/weapons?by=day`, `/matches` без ограничивающего окна;
5. `/api/weapons`, `/api/weapons/{weapon}`, `/api/weapons/{weapon}?by=day` для каждого оружия
   и `/api/weapon-splits`;
6. все вложенные данные карточки матча: раунды, составы сторон, игроки, per-round показатели,
   клатчи, оружие, экономика, utility и голосовые метаданные, если они присутствуют в ответе.

Не входят:

- `POST /api/matches/{id}/tags` и любые другие изменения сайта;
- перебор всех комбинаций фильтров: это повторные агрегаты над теми же сущностями, а не новые данные;
- `.dem`-файлы, если API отдаёт только имя файла, но не публичный URL загрузки;
- позиции на карте и иные поля, которых нет в публичных ответах.

Если во время обхода SPA обнаружится новый публичный GET-endpoint, сборщик обязан остановить
публикацию снимка со статусом `incomplete`, добавить endpoint в контракт и только затем повторить
сбор. Неизвестное не превращается в пустой набор.

## Архитектура хранения

Выбран гибридный вариант с тремя слоями.

### 1. Неизменяемый raw-снимок

Канонический evidence хранится в
`01_raw/whoajor/2026-08-29-full-snapshot/`:

- `manifest.json` — перечень запросов, временные границы, HTTP-метаданные, количество объектов,
  SHA-256 исходного тела и canonical JSON;
- `responses/` — точные JSON-тела всех успешных GET-запросов;
- `contract.json` — версия списка endpoint'ов, ключи сущностей и правила пагинации;
- `validation-report.json` — результаты всех автоматических сверок;
- `whoajor.sqlite` — нормализованная база снимка, детерминированно собираемая из `responses/`.

Raw-ответы и manifest — обязательная коммитимая часть снимка. SQLite также коммитится, если его
размер проходит ограничения GitHub; иначе коммитится детерминированный сжатый образ и команда
распаковки/пересборки. Данные не исключаются из-за размера производного файла.

Старый снимок `2026-08-29-cs2-whoajor-intelligence.json` не меняется и не удаляется.

### 2. Нормализованная SQLite-база

Минимальная схема:

- `snapshots`, `requests`, `source_discrepancies`;
- `matches`, `match_tags`, `match_rounds`, `round_rosters`;
- `players`, `player_aliases`, `match_players`, `player_rounds`;
- `player_match_stats`, `player_side_stats`, `player_clutches`;
- `weapons`, `match_player_weapons`, `player_weapon_stats`, `weapon_splits`;
- `leaderboard_snapshots`, `player_map_snapshots`;
- `draft_config`, `draft_players`, `draft_igls`;
- `meta_maps`, `tags`.

SteamID хранится только как `TEXT`. Денормализованный исходный JSON каждой сущности сохраняется
в колонке `source_json`, чтобы неизвестное поле API не потерялось при нормализации.

Основные ключи: `match_id`, `steamid`, `weapon`; составные ключи включают родительские ID,
например `(match_id, steamid, round)` для `player_rounds`.

### 3. KB-слои

После успешной загрузки создаётся source summary в `02_sources/`; обновляются `index.md`, `log.md`,
`04_synthesis/open-questions.md` и `04_synthesis/contradictions.md`, если полный снимок закрыл пробел
или выявил конфликт. Wiki/synthesis меняются только там, где новые raw-данные действительно меняют
утверждение. Командная сыгранность не выводится из индивидуальных агрегатов автоматически.

## Поток данных

1. Сбор идёт в `.context/whoajor-staging/<snapshot_id>` и не затрагивает опубликованный снимок.
2. Сборщик последовательно запрашивает endpoint'ы с ограничением частоты и retry с backoff.
3. Каждый ответ сначала сохраняется как исходные байты и сразу хешируется.
4. Из обнаруженных match ID, SteamID и оружия строится конечная очередь detail-запросов, включая
   конечные time-series представления `by=day`.
5. Перед завершением повторно читаются `/api/meta` и первая страница `/api/matches`.
6. Валидатор проверяет полноту, схему, ключи, ссылки и арифметические инварианты.
7. Только снимок со статусом `complete` переносится в `01_raw`, после чего из raw строится SQLite.
8. Генератор создаёт source summary и обновления KB.

Запуск повторяем: одинаковые raw-ответы должны давать тот же canonical hash и ту же SQLite-базу
после исключения служебных timestamps из fingerprint данных.

## Полнота и сверка

Обязательные блокирующие проверки:

- число уникальных `match_id` равно `total` из `/api/matches` и `matches` из `/api/meta`;
- для каждого match index существует ровно одна detail-карточка;
- `roundsPlayed == rounds.length`, а каждый SteamID в раундах разрешается через игрока матча;
- каждый `(match_id, steamid, round)` уникален и ссылается на существующий матч/игрока/раунд;
- полный реестр игроков равен объединению SteamID из всех endpoint'ов, а не только 30 игрокам draft;
- каждый элемент `/api/weapons` имеет detail-ответ, а суммы `kills`, `shots` и число игроков
  сверяются с агрегатом;
- `(steamid, weapon)` в `/api/weapon-splits` уникален;
- все SteamID — строки цифр; числовые значения finite; даты и обязательные поля валидны;
- повторный импорт одного raw-набора идемпотентен;
- raw SHA-256, canonical SHA-256 и итоговый root hash пересчитываются независимо.

Известное расхождение `meta.matches=368`, но сумма `meta.maps[].n=365` сохраняется как конфликт
источника и не исправляется молча. `wins + losses` не обязано равняться `matches`, поскольку это
известная оговорка источника.

Дополнительно выполняется детерминированная выборочная сверка не менее 30 сущностей либо 1%:
первая/последняя страницы, старые/новые матчи, все типы endpoint'ов, карты и непустые связи.

## Ошибки и безопасное возобновление

- Любой 4xx/5xx, schema drift, дубль ключа, пропущенная страница или изменившийся `total` делает
  снимок `incomplete`/`unstable`; он не публикуется в `01_raw` и не обновляет KB.
- HTTP 429 и 503 обрабатываются ограниченным exponential backoff с учётом `Retry-After`.
- Возобновление переиспользует только ответы с валидным hash и заново проверяет границы снимка.
- Новые матчи во время offset-пагинации не должны сдвигать данные незаметно: применяется верхняя
  временная граница снимка, overlap страниц и dedup по `match_id`.
- Сервер не публикует rate-limit headers, поэтому сбор по умолчанию последовательный, с небольшим
  интервалом и без конкурентной нагрузки.

## Реализация и команды

Новые модули разделяются по ответственности:

- `scripts/whoajor/collect.mjs` — только HTTP и raw manifest;
- `scripts/whoajor/normalize.mjs` — только raw → SQLite;
- `scripts/whoajor/validate.mjs` — только детерминированные проверки;
- `scripts/whoajor/summarize.mjs` — только raw/SQLite → KB summary;
- `scripts/whoajor/lib/` — контракт, canonical JSON, hashing и schema helpers;
- `scripts/whoajor/test/` — offline fixtures и регрессионные тесты.

Публичные команды:

```bash
pnpm whoajor:collect
pnpm whoajor:validate -- <snapshot-dir>
pnpm whoajor:build-db -- <snapshot-dir>
pnpm whoajor:sync
```

`whoajor:sync` выполняет полный безопасный pipeline и возвращает non-zero до публикации при любой
ошибке. Существующие `kb:doctor`, `kb:verify`, `kb:eval` запускаются после обновления Markdown.

## Критерии готовности

1. Все контрактные GET-endpoint'ы и все обнаруженные detail-сущности сохранены с hash.
2. Snapshot имеет статус `complete`; все блокирующие проверки проходят.
3. SQLite открывается стандартным клиентом и содержит согласованные counts/FK без потерь полей.
4. Повторная сборка SQLite из raw воспроизводит те же данные.
5. Source summary сообщает точные counts, временной диапазон, root hash, ограничения и конфликты.
6. `pnpm whoajor:test`, `pnpm kb:doctor`, citation/provenance gate и `pnpm kb:eval` зелёные.
7. Изменение закоммичено и отправлено в `main` с инструкцией проверки без чтения кода.
